%% Draft abstract: retain the argument and contribution; add results after evaluation.
\begin{abstract}
\draft{Mechanized language specifications offer a basis for testing implementations, but a property-based test also depends on the correctness of its property, generator, and oracle.}
\draft{These components are difficult to assess by sampling alone, especially when an agent writes them.}
\draft{We introduce a SpecTec-to-Lean translator to state proof obligations over the P4-SpecTec specification; the translation has passed validation tests.}
\draft{We propose a workflow in which an agent states a property in a restricted SpecTec-like language, with a Lean interpretation over the translated specification.}
\draft{The restriction is intended to support automatic derivation of an input generator, an oracle, and their proof obligations from the property.}
\draft{The proposed workflow checks the property and the generator's soundness and completeness, and states in Lean how an abstract machine decides the conclusion used as an oracle.}
\draft{We study this approach with P4-SpecTec and evaluate whether it can produce usable proven tests and expose implementation bugs.}
\draft{The resulting guarantees depend on the empirically validated translation and the connection between Lean values and implementation observations.}
\end{abstract}
